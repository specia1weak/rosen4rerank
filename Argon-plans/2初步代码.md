### 三、 满足 Leader 要求的模型架构：同特征集输入 + 相乘输出

Leader 要求：**对比基线和我们的模型必须吃完全相同的特征集 $X_{\text{all}} = [\text{Block 1}, \text{Block 2}, \text{Block 3}, \text{Block 4}]$，且我们的模型最终输出必须是 $\hat{y}_t = \gamma_t \times (1 - h_t)$**。

为了同时应对你们之前发现的 **“前 20 分钟风险上升、随后回落的驼峰形曲线”**，我们在左塔使用 **2 分量混合威布尔条件存活函数（2-Mixture Weibull Conditional Survival）**。下面是可以直接放进你工程里的核心 PyTorch 模型结构：

```python
import torch
import torch.nn as nn
import torch.nn.functional as F

class DecoupledSurvivalExitModel(nn.Module):
    """
    满足 Leader 要求：
    1. 预算塔和内容塔接收完全相同的特征矩阵 x_all
    2. 预算塔通过混合威布尔生存公式注入物理时钟归纳偏置 (e_t, delta_t)
    3. 最终预测严格为两者相乘: p_continue = gamma_t * (1 - h_t)
    """
    def __init__(self, in_dim: int, hidden_dim: int = 64, n_components: int = 2):
        super().__init__()
        self.K = n_components
        
        # 左塔：时间预算参数预测网 (吃全特征 x_all，输出混合威布尔的权重 pi、尺度 lam、形状 z)
        self.budget_net = nn.Sequential(
            nn.Linear(in_dim, hidden_dim),
            nn.SiLU(),
            nn.Linear(hidden_dim, self.K * 3)  # pi_k, lam_k, z_k
        )
        
        # 右塔：黑盒内容留存网 (吃完全相同的全特征 x_all，输出 1 - h_t)
        self.content_net = nn.Sequential(
            nn.Linear(in_dim, hidden_dim),
            nn.SiLU(),
            nn.Dropout(0.1),
            nn.Linear(hidden_dim, hidden_dim // 2),
            nn.SiLU(),
            nn.Linear(hidden_dim // 2, 1)
        )

    def forward_survival(self, x_all: torch.Tensor, e_t_min: torch.Tensor, delta_t_min: torch.Tensor):
        """
        e_t_min: 当前已消耗时长（单位：分钟，例如 elapsed_time_s / 60.0），shape [B]
        delta_t_min: 度过本屏的步长（单位：分钟，可取固定步长 1.0 或当屏期望时长），shape [B]
        """
        raw = self.budget_net(x_all).view(-1, self.K, 3)
        
        # 1. 混合权重 pi_k (和为 1)
        pi = F.softmax(raw[:, :, 0], dim=-1)                       # [B, K]
        # 2. 尺度参数 lambda_k > 0.1 (单位：分钟，控制预算长短)
        lam = F.softplus(raw[:, :, 1]) + 0.1                       # [B, K]
        # 3. 形状参数 z_k > 0.5 (允许 K=2 个分量组合出“先升后降”的驼峰风险率)
        z = F.softplus(raw[:, :, 2]) + 0.5                         # [B, K]
        
        e_curr = e_t_min.unsqueeze(-1).clamp(min=0.0)              # [B, 1]
        e_next = (e_t_min + delta_t_min).unsqueeze(-1).clamp(min=1e-3)
        
        # 计算 S(e_t) 和 S(e_t + delta_t)
        # 为防止大指数溢出，对 (e / lam)^z 做上限截断
        hazard_curr = ((e_curr / lam).clamp(max=20.0)) ** z
        hazard_next = ((e_next / lam).clamp(max=20.0)) ** z
        
        S_curr = (pi * torch.exp(-hazard_curr)).sum(dim=-1).clamp(min=1e-6) # [B] 供下游 AWR 算 kappa_t = 1/S(e_t)
        S_next = (pi * torch.exp(-hazard_next)).sum(dim=-1).clamp(min=1e-7) # [B]
        
        # 条件存活率 gamma(e_t) = S(e_t + delta) / S(e_t)
        gamma_t = (S_next / S_curr).clamp(min=1e-5, max=1.0 - 1e-5)
        return gamma_t, S_curr

    def forward(self, x_all: torch.Tensor, e_t_min: torch.Tensor, delta_t_min: torch.Tensor):
        gamma_t, S_curr = self.forward_survival(x_all, e_t_min, delta_t_min)
        content_stay = torch.sigmoid(self.content_net(x_all).squeeze(-1))  # 1 - h_t
        
        # 严格相乘作为最终预测概率
        p_continue = gamma_t * content_stay
        return p_continue, gamma_t, content_stay, S_curr

```

**训练技巧（复刻 CAVE 的防抢梯度机制）**：

* **Stage 1（前 3 个 Epoch，预热生存底座）**：只用 `gamma_t` 和真实标签 `y_continue` 算 BCE Loss 更新 `budget_net`，让威布尔先把时间流逝的基准曲线拟准；


* **Stage 2（后 5 个 Epoch，联合微调）**：把 `budget_net` 的学习率设为 `1e-4`（或冻结），`content_net` 的学习率设为 `1e-3`，用相乘后的 `p_continue = gamma_t * content_stay` 算 BCE Loss。

### 1. 算已消耗时间 $e_t$ 时：直接用“首尾时间戳相减 + 最后一个视频的播放时长”

我上一轮建议你把前面每个视频的 `play_time_ms`、`comment_stay_time`、`profile_stay_time` 一条条加起来算已消耗时间 $e_t$。**Leader 的意思是：完全不用管中间过程！**

因为 KR 日志里的 `time_ms` 记录的是每个视频**开始曝光（或产生记录）的现实挂钟时间戳**：

* 假设本场 Session 的第 1 个视频开始于 $t_1$，当前这一屏（Request）的最后一个视频是第 $k$ 个视频，开始于 $t_k$。
* 那么从第 $1$ 个视频到第 $k-1$ 个视频，用户无论是认认真真看完了（实际观看时长），还是在评论区发呆、切出去回微信、上下划屏停顿（交互间隔时长），**所有流逝掉的现实时间，已经 100% 包含在时间戳差值 $(t_k - t_1)$ 里面了！** 中间每一项具体是多少，在数学上会直接首尾相消，根本不需要算。
* **为什么说“除了最后一个视频”？**
因为 $t_k$ 只是第 $k$ 个视频（当前屏最后一个视频，或整场 Session 最后一个视频）**开始**的时刻。当用户刷完第 $k$ 个视频决定退出的那一刻，你不能拿 $t_{k+1} - t_1$ 来算（因为对于 Session 的最后一个视频，$t_{k+1}$ 已经是几小时后下一场 Session 的时间戳了；对于当前屏，看 $t_{k+1}$ 相当于偷看了下一屏的未来信息）。
所以，你在算截至第 $k$ 个视频结束时的累计流逝时间 $e_t$ 时，**唯一需要用到实际观看时长的，只有第 $k$ 个视频（最后一个视频）本身**：

$$e_t = \big(\text{time\_ms}[k] - \text{time\_ms}[1]\big) + \text{play\_time\_ms}[k]$$

### 2. 算交互间隔时：只用来判断“谁是 Session 的最后一个视频”

“交互间隔时长”（相邻两个视频之间的时间空隙 $\Delta t_i = \text{time\_ms}[i+1] - (\text{time\_ms}[i] + \text{play\_time\_ms}[i])$）在现阶段只有一个用途：

* **切分 Session 边界（找出最后一个视频）**：当第 $i$ 个视频结束之后，距离第 $i+1$ 个视频的间隔超过了阈值（比如 $> 30$ 分钟），我们就判定第 $i$ 个视频是本场 Session 的**最后一个视频**（即本屏标签 $y_t = 0$，触发退出）。


* **Session 内部一律忽略**：只要两个视频之间的间隔没超过 30 分钟（即它不是最后一个视频），中间隔了 1 秒还是隔了 5 分钟，现阶段完全不在乎，既不剔除也不单独拎出来做特征。

### 3. 明确“现阶段（6.1 退出预实验）”的任务边界：只看自然挂钟时间，不抠有效播放时长

Leader 强调“现阶段不在乎实际观看时长”，是因为你们把实验分成了两步走：

* **后一阶段（6.2 Generator / 6.3 Evaluator 算 LTV $G_t$）**：那时候你们要优化的是平台指标（用户真正盯着屏幕看的累计有效播放时长 $\sum \text{play\_time\_ms}$），所以到那时候才需要去累加每个视频的实际观看时长 $w_t$ 和 $G_t$。


* **现阶段（6.1 预实验，验证 $\gamma(e_t) \times (1 - h_t)$ 预测退出 $y_t \in \{0,1\}$）**：


1. 决定用户“时间预算耗没耗尽（$\gamma(e_t)$）”的是**现实世界走过的自然时间（挂钟时间 $e_t$）**，而不是用户纯粹看视频的有效秒数（哪怕用户中间刷评论区花了 5 分钟，他的午休时间也照样少了 5 分钟）；
2. 正如你们之前在诊断报告第七节验证过的，单屏内部到底有几个视频没播放（`n_unplayed`）、实际看了百分之几（`played_frac`），对预测退出的 AUC 只有 `0.4991` / `0.5001`。所以现阶段做内容特征时，直接用视频本身的静态属性/历史先验即可，不用去纠结单条视频的实际播放秒数。
